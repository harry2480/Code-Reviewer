# Phase 5: フロントエンド（ダッシュボード・レビュー履歴・設定） 実装計画

## 目的

**個人開発者（運用者本人）が、GitHub PR に投稿された AI レビューの動作状況・履歴・予算消費・言語別ルール設定を、コードを開かずブラウザで把握・調整できる状態にするため。**

具体的には、Phase 1〜4 で構築したバックエンド（DDD 4 層、4 つの眼レビューエンジン、ポリグロット・エキスパート、自己修正、背景抽出）を運用面から制御する Web UI を整備し、以下 3 つの不便を解消する：

| 解消する不便 | 提供する画面 |
|---|---|
| AI レビューが動いているのか / 予算をどれくらい使ったのかが、ログを開かないと分からない | ダッシュボード（接続状態 + 統計サマリー + 予算消費） |
| 過去にどの PR にどんな指摘をしたかを GitHub に逐一遡らないと参照できない | レビュー履歴一覧 + 詳細（Analysis Chain / Suggested Changes） |
| 言語別ルール ON/OFF や日次予算上限を変更するのに、環境変数や DB を直接いじるしかない | 設定ページ（言語別ルール切替 / 予算上限編集） |

## 前提条件

- **Phase 1 完了済み**: `apps/webapp/` 配下に DDD 4 層スケルトンが存在する。`ReviewComment` / `Budget` / `LanguageExpert` モデル、`ReviewCommentRepository` / `BudgetRepository` interface が整備済み。
- **Phase 2 / 3 / 4 完了済みを想定**: ReviewEngine Service、PolyglotExpert Service、SelfRefinement Service、ContextExtractor Gateway が `develop` に存在する。Phase 5 は本番データ書き込み元（バックエンドのレビュー実行フロー）が動いていることを前提に、その結果を表示する。
- **Phase 6 未着手**: GitHub App Webhook / Checks API は未実装。Phase 5 のダッシュボードでは GitHub App 接続状態を**環境変数の存在チェックで簡易判定**し、Phase 6 で実 API 判定に差し替える。
- **既存フロントエンド資産**: `apps/webapp/src/app/` に `/`（TOP）と `/jokes`（既存デモ）、`apps/webapp/src/frontend/components/ui/` に shadcn/ui コンポーネント群（button, card, badge, table, pagination, switch, dialog 等）が配備済み。

> 本ドキュメントは Phase 1〜4 が `develop` にマージされた状態を前提に、`feature/phase5-frontend-dashboard` ブランチを切ることを想定する。

## 必要な環境変数

Phase 5 では新規追加が必要な環境変数は**ゼロ**。既存の環境変数を参照のみする。

| 環境変数 | 用途 | Phase 5 での利用箇所 | 未設定時の挙動 |
|---|---|---|---|
| `DATABASE_URL` | Prisma 接続（既存） | 全 loader / 全 server action（Repository 経由） | バックエンド全体が動かない（既存挙動） |
| `GITHUB_APP_ID` | GitHub App 識別子（既存定義／未配備の可能性） | ダッシュボードの接続状態判定（存在チェックのみ） | 「Not Connected」表示 |
| `GITHUB_APP_PRIVATE_KEY` | GitHub App 秘密鍵（既存定義／未配備の可能性） | 同上（存在チェックのみ） | 同上 |

`GITHUB_APP_ID` / `GITHUB_APP_PRIVATE_KEY` は Phase 6 で本格利用するが、Phase 5 では値の存在のみを参照する placeholder 用途。実 API 判定は Phase 6 で `GitHubAppGateway` を導入して差し替える。

## 設計方針

### 全体アーキテクチャ

Phase 5 は **「バックエンド DDD 4 層を一切壊さず、`presentation/loaders/` と `presentation/actions/` を増やすだけで Server Component から呼び出す」** 方針で構成する。新規ページ・新規 UI コンポーネントは `apps/webapp/src/app/(authenticated)/` と `apps/webapp/src/frontend/features/` 配下に追加する。

```
[ブラウザ]
   ↓
[Next.js App Router (Server Component)]
   ↓ async loader 呼び出し
[presentation/loaders/*.loader.ts]              ← 新規 4 ファイル
   ↓
[application/usecases/*.usecase.ts]             ← 新規 4 ファイル
   ↓
[domain/repositories/*.repository.ts (interface)] ← 既存 2 + 新規 2
   ↓ implements
[infrastructure/repositories/*.repository.ts]    ← 既存 2 + 新規 2

[ブラウザのフォーム送信]
   ↓ Server Action
[presentation/actions/*.action.ts]              ← 新規 2 ファイル
   ↓
[application/usecases/*.usecase.ts]             ← 上記と共通
   ↓
[同上 Repository 経由で永続化]
   ↓ revalidatePath で UI 再生成
```

依存方向は既存規約（`presentation → application → domain ← infrastructure`）を完全に踏襲する。フロントエンド側は loader が返す型のみに依存し、Repository / Adapter には直接触れない。

### 認証戦略（ルートグループのみ作成）

フロントエンドアーキテクチャ.md に記載の `app/(authenticated)/` ルートグループを **作成だけする**。Phase 5 時点では認証ロジック（middleware / NextAuth 等）は導入せず、グループ内のページは無認証アクセス可能。Phase 6 以降で middleware を追加する際、ファイル移動なしで保護対象を区別できる構造にしておく。

```
apps/webapp/src/app/
├── (authenticated)/
│   ├── dashboard/page.tsx
│   ├── review-history/
│   │   ├── page.tsx
│   │   └── [id]/page.tsx
│   ├── settings/page.tsx
│   └── layout.tsx        ← 認証要件があれば後で middleware を効かせるための共通レイアウト
├── jokes/page.tsx        ← 既存（未変更）
├── layout.tsx            ← 既存。サイドバー差し替え
└── page.tsx              ← 既存（TOP）
```

`(authenticated)/layout.tsx` には「認証チェック予定」のコメントは置かない（[CLAUDE.md] に従い「将来〜のための」コメントは禁止）。Phase 6 で必要になった時点で middleware ファイルを新設する。

### ページ構成

#### `/dashboard`（Server Component + ISR 10 分）

| 表示要素 | データソース |
|---|---|
| GitHub App 接続バッジ（Connected / Not Connected） | `process.env.GITHUB_APP_ID && process.env.GITHUB_APP_PRIVATE_KEY` の存在チェック |
| 本日のレビュー数 | `ReviewSessionRepository.countByDate(today)` |
| 本日のセキュリティ検出数 | `ReviewCommentRepository.countByPerspectiveAndDate('security', today)` |
| 本日の予算消費（progress bar：使用 / 上限） | `BudgetRepository.findByDate(today)` |
| 対応言語バッジ一覧 | `LanguageExpert` の固定 6 言語（DB 不要） |
| 直近 5 件のレビューサマリー | `ReviewSessionRepository.findRecent(5)` |

ISR 設定: `export const revalidate = 600` （10 分）。フロントエンドアーキテクチャ.md の「統計は ISR で 10 分ごと再生成」に準拠。

#### `/review-history`（Server Component、ページネーション付き）

URL クエリパラメータ:
- `?page=N` （デフォルト 1、1 ページ 20 件）
- `?language=typescript|python|...|all` （絞り込み）
- `?status=success|failed|all` （絞り込み）

| 表示要素 | データソース |
|---|---|
| レビュー履歴テーブル（PR タイトル / GitHub リンク / 言語 / ステータス / 4 つの眼スコア / 実行時刻 / コメント数） | `ReviewSessionRepository.findPaginated({page, perPage, filters})` |
| ページネーション UI | shadcn/ui `pagination` |
| 言語・ステータスフィルタ | shadcn/ui `select`（クライアントコンポーネントで URL 操作） |

各行クリックで `/review-history/[id]` に遷移。

#### `/review-history/[id]`（Server Component）

| 表示要素 | データソース |
|---|---|
| PR メタ情報（owner/repo/PR# 番、タイトル、対象言語、実行時刻、合計トークン） | `ReviewSessionRepository.findById(id)` |
| 4 つの眼スコア（Logic / Security / Efficiency / Readability） | session 内の集計値（後述） |
| Analysis Chain（`<details>` で折りたたみ） | session に保存された `analysisChain` テキスト（後述スキーマ） |
| ReviewComment 一覧（perspective バッジ・severity 色分け・ファイルパス・行番号・本文・Suggested Code） | `ReviewCommentRepository.findBySessionId(id)` |

スタイルガイド.md の「PR レビューコメント表示」と「Analysis Chain」のパターンを踏襲する。

#### `/settings`（Server Component + Server Actions）

| 表示要素 | データソース | 編集 Action |
|---|---|---|
| GitHub App 設定状況（環境変数の存在チェックの結果） | `process.env.GITHUB_APP_ID` 等 | （編集なし、表示のみ） |
| 言語別ルール ON/OFF（typescript / python / swift / php / go / rust の 6 件、`switch` UI） | `LanguageRuleSettingRepository.findAll()` | `toggleLanguageRuleAction(language, enabled)` |
| 日次予算上限（数値入力 + 保存ボタン） | `BudgetRepository.findByDate(today)` の `dailyLimitUsd` | `updateDailyLimitAction(usd)` |

Server Action 実行後は `revalidatePath('/settings')` で再描画。フロントエンド規約.md の「ミューテーションは Server Actions」に従う。

### データソースとテーブル設計

#### 新規テーブル 1: `ReviewSession`

レビュー実行 1 回（PR 1 つに対する 4 つの眼の一連の処理）をまとめるアグリゲート。`ReviewComment` の親エンティティとして機能する。Phase 4 までは「コメント単位」での永続化のみだったが、履歴一覧のために PR 単位の集約レコードを導入する。

| カラム | 型 | 用途 |
|---|---|---|
| `id` | String (cuid) | PK |
| `owner` | String | GitHub オーナー |
| `repo` | String | GitHub リポジトリ |
| `prNumber` | Int | PR 番号 |
| `prTitle` | String | PR タイトル（履歴表示用） |
| `prUrl` | String | PR の GitHub URL（履歴行のリンク用） |
| `status` | String | `success` / `failed` / `skipped` |
| `detectedLanguages` | String[] | 検出言語リスト（Postgres `text[]`） |
| `logicScore` / `securityScore` / `efficiencyScore` / `readabilityScore` | Int? | 4 つの眼スコア（0-10、null 許容） |
| `totalTokens` | Int | 当該レビューの累積トークン |
| `analysisChain` | String? | 推論プロセスのテキスト（`<details>` 表示用、長文許容） |
| `durationMs` | Int | 実行時間（ms） |
| `createdAt` | DateTime | レビュー実行時刻 |

`ReviewComment` 側に `sessionId String` を追加して FK 参照する（Prisma の relation で 1:N）。これにより `ReviewSessionRepository.findById` から `ReviewComment[]` を 1 クエリで取得可能になる。

#### 新規テーブル 2: `LanguageRuleSetting`

言語別エキスパート・ルールの ON/OFF を永続化する。Phase 3 で実装される `PolyglotExpert` がレビュー実行時にこのテーブルを参照し、無効化された言語のプロンプト注入をスキップする。

| カラム | 型 | 用途 |
|---|---|---|
| `language` | String | PK（`typescript` / `python` / `swift` / `php` / `go` / `rust`） |
| `enabled` | Boolean | デフォルト `true` |
| `updatedAt` | DateTime | 最終更新時刻 |

設定ページの保存 Action は upsert で動作する。テーブルに row が無い言語は「有効（デフォルト true）」と解釈する初期化ロジックを `LanguageRuleSettingRepository` 側で持つ。

#### 既存テーブルへの変更

- `ReviewComment` に `sessionId String` カラムを追加（FK to `ReviewSession.id`）。
- 既存 `ReviewComment.model.ts` の `create` / `reconstruct` ファクトリに `sessionId` 引数を追加する。これは破壊的変更だが、Phase 4 のレビュー実行フローも同時に修正対象に含めるため整合性を保つ。
- `Budget` テーブルは変更なし。設定ページからの編集は既存の `dailyLimitUsd` を上書きする。

### Domain 層への追加

```
apps/webapp/src/backend/domain/
├── models/
│   ├── review-session.model.ts            ← 新規（Rich Domain Model）
│   └── language-rule-setting.model.ts     ← 新規（Rich Domain Model）
└── repositories/
    ├── review-session.repository.ts       ← 新規 interface
    └── language-rule-setting.repository.ts ← 新規 interface
```

`ReviewSession.create` ファクトリは以下の不変条件を強制する：

- `status` は `success` / `failed` / `skipped` のいずれか
- 各 score は `null` または 0〜10 の整数
- `prNumber >= 1`
- `owner` / `repo` / `prTitle` / `prUrl` は trim 後 1 文字以上
- `detectedLanguages` は重複なし、`SupportedLanguage` の値のみ（`LanguageExpert` 既存定数を再利用）

`LanguageRuleSetting.create` ファクトリは：

- `language` は `SupportedLanguage` のみ
- `enabled` は boolean

Repository interface は規約 [docs/リポジトリ層設計規約.md] に従い、戻り値は domain メソッドからは生エンティティを返す形にしつつ、内部エラーは `Result<T, E>` で表現する（既存 `ReviewCommentRepository` の方針に揃える）。具体的なシグネチャは実装着手時に Phase 1 / 4 の実装に合わせて整える。

#### loader の戻り値設計

loader は **DOM 側で扱いやすいプリミティブ型のみ**を返す（Date は ISO 文字列に変換、enum は string に変換）。これは既存 `joke.loader.ts` の方針を踏襲する。これにより Server → Client コンポーネント境界をまたいでも serializable で、フロントエンドコンポーネントは Prisma の生型に依存せずテスト可能になる。

例：

```typescript
// 戻り値の型イメージ（実装は当該ファイルで）
export type DashboardStats = {
  githubAppConnected: boolean;
  todayReviewCount: number;
  todaySecurityFindings: number;
  budget: { dailyLimitUsd: number; usedUsd: number; remainingUsd: number };
  supportedLanguages: SupportedLanguage[];
  recentSessions: { id: string; prTitle: string; prUrl: string; status: string; createdAt: string }[];
};
```

#### action の責務

`settings.action.ts` の各エクスポート関数は `'use server'` を頭に付与し、フォーム送信を受け取って UseCase を呼び出し、`revalidatePath` で UI を更新するのみ。バリデーションは UseCase 側 + Domain Model の `create` ファクトリに委譲する（フロントエンド規約.md 準拠）。

#### Server / Client コンポーネントの境界

- データ取得は loader（Server Component 内で `await`）。Client Component で `useEffect + fetch` は禁止。
- `'use client'` を付けるのは以下のみ：
  - `review-history-filters.tsx`（URL クエリ操作のためルーターフックを利用）
  - `language-rule-toggle.tsx`（Switch のクリックイベント → Server Action）
  - `budget-limit-form.tsx`（フォーム入力 → Server Action）
- 全 UI は shadcn/ui コンポーネントを優先利用（既存 `components/ui/` から `card` / `badge` / `button` / `pagination` / `select` / `switch` / `table` / `input` / `progress` / `dialog` を使用）。スタイルガイド.md の「shadcn/ui 優先 / ハードコード色禁止 / Mobile First」に準拠。
