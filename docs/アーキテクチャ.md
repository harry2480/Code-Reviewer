# AI-Review-Agent アーキテクチャ設計規約

pnpm workspace + Hono/Node.js (Vercel Serverless Functions) における DDD バックエンド設計規約。
`src/backend/` 配下に適用する。

GitHub PR における自動レビュー実行、複数言語エキスパート・プロンプト動的注入、自己修正（二段階検証）を実現するための設計。

## DDD 4 層構造

| 層 | ディレクトリ | 責務 |
|---|---|---|
| presentation | `presentation/composition/` `loaders/` `actions/` | GitHub Webhook 受信、PR 情報取得、レビューコメント投稿。Checks API による進捗表示 |
| application | `application/usecases/` | PR レビュー実行フロー、差分解析、エキスパート・プロンプト生成、自己修正オーケストレーション |
| domain | `domain/models/` `services/` `gateways/` `repositories/` | ビジネスルール。「4つの眼」（ロジック・セキュリティ・効率性・可読性）、ポリグロット・エキスパート、二段階検証、予算管理。外部依存なし |
| infrastructure | `infrastructure/adapters/` `repositories/` `db/` | AI API（Gemini / OpenRouter）、GitHub API、Upstash QStash/Redis 実装 |

---

## 依存方向（厳守）

`presentation → application → domain ← infrastructure`

- **domain は最内層。** 他層への依存禁止。ビジネスロジック（4つの眼、ポリグロット・エキスパート、自己修正）を完全に閉じ込める
- **application は domain にのみ依存。** infrastructure への直接依存禁止（Gateway interface 経由）。UI ロジック（Webhook、Checks API）は presentation に委譲
- **infrastructure は domain/gateways, domain/repositories に依存。** interface を implements する。AI API、GitHub API、Redis のリトライ・エラーハンドリング実装
- **presentation/loaders, actions は application + presentation/composition にのみ依存。** domain・infrastructure の直接参照禁止
- **presentation/composition は全層を参照可。** UseCase に infrastructure 実装を注入し、環境変数に応じて AI エンジン（Gemini vs OpenRouter）を切り替える唯一の場所

---

## presentation 層: composition / loaders / actions

Hono ルーター + Vercel Serverless Functions の唯一の接続点。**API Route は原則使用しない。** Hono で Webhook ハンドリング。

| 種別 | 責務 | トリガー |
|---|---|---|
| composition | UseCase + infrastructure 実装の組み立て（Composition Root）。AI エンジン切り替え | loader, action |
| loader | PR 情報取得（GitHub API 経由） | Hono GET エンドポイント |
| action | GitHub Webhook 受信、PR レビュー実行トリガー、レビューコメント投稿 | Hono POST エンドポイント (`'use server'` マーク不要。Hono ハンドラで実行) |

- **loader**: GitHub API から PR 差分・メタデータを取得し、UseCase に渡す
- **action**: Webhook ペイロードを受け取り、composition から UseCase を取得して実行。非同期処理は Upstash QStash にキュー
- **composition**: 環境変数 (`AI_ENGINE=gemini | openrouter`, `STUB_MODE=true | false`) に応じて AI アダプタを選択。本番環境では実AI、テスト環境では Stub

## domain 層: ビジネスルール

### 「4つの眼」の実装

ReviewEngine Service が以下の 4 つの視点で評価。各視点をドメインモデルで定義。

1. **ロジック**: 境界値、例外処理、実行時エラー、破壊的変更の検出
2. **セキュリティ**: シークレット露出（自動マスク）、脆弱なパターンの指摘
3. **効率性**: 計算量（O(n) 等）、冗長なリソース消費、キャッシュ戦略
4. **可読性**: 命名規則、SOLID原則、プロジェクト規約遵守

各視点ごとにスコア化し、ReviewComment モデルに格納。

### ポリグロット・エキスパート・モジュール

PR 内の拡張子を判定（TypeScript, Python, Swift, PHP, Go, Rust）し、言語固有ルールを動的に注入。

```typescript
// domain/models/language-expert.model.ts
export type SupportedLanguage = 'typescript' | 'python' | 'swift' | 'php' | 'go' | 'rust';

export class LanguageExpert {
  static fromExtension(ext: string): SupportedLanguage | null {
    // 拡張子から言語判定
  }
  
  rules(): ExpertRule[] {
    // 言語別ルール返却
  }
}
```

### 自己修正（二段階検証）

SelfRefinement Service が生成フェーズ → 検証フェーズを実行。

1. **生成フェーズ**: AI がレビューコメント生成
2. **検証フェーズ**: 別プロンプトで「ハルシネーション検出」「提案コード確認」「根拠確認」

検証で問題発見時は regenerate。

### 背景抽出

ContextExtractor Gateway が以下を検索：

- 直近のコミットメッセージ（コンテキスト）
- 呼び出し元の検索（影響範囲）

推論に反映し、より精密なレビューを実現。

### 予算管理・ハードリミット

BudgetManager Service が：

- トークン消費量をリアルタイム集計
- 1日の上限（例: 0.5 USD = 約 77 円）を超えたら即停止
- Redis に ログ記録

## ドメインモデル設計

**Rich Domain Model を徹底。Anemic Domain Model 禁止。**

- 値の生成・検証・変換はモデル自身のファクトリメソッド / インスタンスメソッドで行う
- ドメイン不変条件はファクトリメソッド / コンストラクタで強制
- 例: `ReviewComment.create(...)` で詳細推論・提案コード・提案の正当性を同時に検証

---

## サービス実装規約

**全サービス（domain service, UseCase）はクラスベース + コンストラクタ DI。関数エクスポートは禁止。**

```typescript
export class ExecutePrReviewUseCase {
  constructor(
    private readonly reviewEngine: ReviewEngine,
    private readonly aiGateway: AiEngineGateway,
    private readonly githubGateway: GitHubApiGateway,
    private readonly contextExtractor: ContextExtractorGateway,
    private readonly budgetManager: BudgetManager
  ) {}

  async execute(prPayload: PullRequest): Promise<Result<ReviewComment[], ReviewError>> {
    // ロジック
  }
}
```

- コンストラクタの `private readonly` で依存を受け取る
- エラーは `Result<T, E>` で返す（throw 禁止）
- ビジネスロジックは `execute()` 等の public メソッドで公開

## Gateway / Repository パターン

| 種類 | interface 配置 | 実装配置 | 例 |
|---|---|---|---|
| Gateway | `domain/gateways/` | `infrastructure/adapters/` | AI Engine, GitHub API, Context Extractor |
| Repository | `domain/repositories/` | `infrastructure/repositories/` | Review History, Budget Ledger |

**Stub 実装必須**: 本番実装と同じ interface を実装した Stub を用意。composition で環境変数に応じて切り替え。

---

## エラーハンドリング

- **domain**: ビジネス例外は `Result<T, E>` で返す。throw 禁止
- **application**: UseCase が domain の Result を受け取り、ハンドリング
- **infrastructure**: API エラー・ネットワークエラーは throw。adapter が retry/fallback 処理実装
- **presentation**: action が例外を catch し、適切な HTTP ステータスを返す
