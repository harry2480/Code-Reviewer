# AI-Review-Agent テストガイドライン

このドキュメントは、AI-Review-Agent におけるテストの書き方・運用方法をまとめたガイドラインです。基本ルールは `CLAUDE.md` にも記載しています。

DDD 4層アーキテクチャ（domain → application → infrastructure ← presentation）に基づき、各層で異なるテスト戦略を採用します。

---

## テストの種類と構成

プロジェクトでは以下の種類のテストを運用します。

| 種類 | 配置場所 | 実行環境 | 実行コマンド | 用途 | 対象層 |
|------|----------|----------|-------------|------|--------|
| ユニットテスト | `test/unit/**/*.test.ts` | Vitest | `pnpm test:unit` | ビジネスロジック（Domain/Application） | Domain, Application |
| 統合テスト | `test/integration/**/*.test.ts` | Vitest + DB | `pnpm test:integration` | インフラ実装・DB操作の検証 | Infrastructure |
| E2E テスト | `tests/e2e/**/*.spec.ts` | Playwright + Browser | `pnpm test:e2e`（未実装） | フロントエンド・バックエンド統合 | Presentation |

---

## CI 実行フロー

PR 作成・Push 時に、`.github/workflows/` で以下が順次実行されます。

```
PR Created / Push to main
  ├── Lint + Format (pnpm lint:fix)
  ├── TypeScript 型チェック (pnpm typecheck)
  ├── Prisma generate (pnpm prisma generate)
  ├── Unit Test (pnpm test:unit)
  ├── Integration Test (pnpm test:integration) ← INTEGRATION_TEST=true 時のみ
  └── Dependency Cruiser (pnpm depcruise) ← DDD 4層依存ルール検証
```

全ステップがパスするとマージ可能になります。

## Unit Test（ユニットテスト）

Domain + Application 層の純粋なビジネスロジックテスト。**外部依存（DB、API、ファイルシステム）は一切使わない。**

### 対象

| 層 | モジュール | 例 |
|---|---|---|
| **Domain** | Models、Services、Repositories（interface） | `ReviewComment.model.ts`、`ReviewEngine.service.ts` |
| **Application** | UseCases | `ExecutePrReviewUseCase.ts`、`RefineReviewCommentUseCase.ts` |

### 配置ルール

実装ファイルと同じディレクトリ階層に `*.test.ts` として配置。`test/unit/` ディレクトリ構造が `src/` を mirror する。

```
src/backend/
├── domain/
│   ├── models/
│   │   ├── review-comment.model.ts
│   │   └── ...
│   └── services/
│       ├── review-engine.service.ts
│       └── ...
└── application/
    └── usecases/
        ├── execute-pr-review.usecase.ts
        └── ...

test/unit/
├── domain/
│   ├── models/
│   │   ├── review-comment.model.test.ts    ← mirror 構造
│   │   └── ...
│   └── services/
│       ├── review-engine.service.test.ts
│       └── ...
└── application/
    └── usecases/
        ├── execute-pr-review.usecase.test.ts
        └── ...
```

### ポイント

#### 1. 外部依存（Gateway）は Mock する

Gateway interface は Fake/Mock 実装に置き換える。

```typescript
// 良い例: Gateway を Mock で注入
import { ReviewEngineService } from '@/backend/domain/services/review-engine.service'
import { MockAiGateway } from '@/test/unit/domain/services/mocks/ai-gateway.mock'

describe('ReviewEngineService', () => {
  it('should evaluate PR with 4-eye review', async () => {
    const mockAi = new MockAiGateway()
    mockAi.setResponse({ analysis: '...' })
    
    const service = new ReviewEngineService(mockAi)
    const result = await service.execute(prDiff)
    
    expect(result.isSuccess).toBe(true)
    expect(result.value.reviews).toHaveLength(4) // Logic, Security, Efficiency, Readability
  })
})
```

#### 2. Rich Domain Model を徹底的にテスト

ファクトリメソッド、インスタンスメソッド、不変条件を検証。

```typescript
// 良い例: モデルの生成ルール・検証
describe('ReviewComment.create()', () => {
  it('should reject invalid analysis', () => {
    const result = ReviewComment.create({
      perspective: 'logic',
      score: 15, // 0-10 のみ有効
      message: '...'
    })
    expect(result.isError).toBe(true)
    expect(result.error.code).toBe('INVALID_SCORE')
  })

  it('should generate suggestion code only for valid changes', () => {
    const result = ReviewComment.create({
      perspective: 'logic',
      score: 7,
      message: '...',
      suggestedCode: invalidCode // syntax error
    })
    expect(result.isError).toBe(true)
  })
})
```

#### 3. ビジネスルール・不変条件を検証

DDD では Domain Model の不変条件は絶対。テストで検証。

```typescript
// 良い例: 予算管理の不変条件
describe('BudgetManager', () => {
  it('should reject spending when daily limit exceeded', () => {
    const manager = new BudgetManager({ dailyLimitUsd: 0.5 })
    
    manager.spend(0.4)  // OK
    manager.spend(0.15) // OK
    
    const result = manager.spend(0.05) // 合計 0.6 USD → 超過
    expect(result.isError).toBe(true)
    expect(result.error).toBe('DAILY_LIMIT_EXCEEDED')
  })
})
```

#### 4. エラーハンドリングを網羅

Domain では `Result<T, E>` で返すため、Success/Error 両ケースをテスト。

```typescript
// 良い例: Success/Error 両パス
describe('PolyglotExpert', () => {
  it('should identify language correctly', () => {
    const expert = new PolyglotExpert()
    const result = expert.selectByExtension('.ts')
    expect(result.isSuccess).toBe(true)
    expect(result.value.language).toBe('typescript')
  })

  it('should return error for unsupported language', () => {
    const expert = new PolyglotExpert()
    const result = expert.selectByExtension('.xyz')
    expect(result.isError).toBe(true)
    expect(result.error).toBe('UNSUPPORTED_LANGUAGE')
  })
})
```

## Integration Test（統合テスト）

Infrastructure 層の実装・Database 操作の検証。**実際の DB（テスト用）に接続してテスト。**

### 対象

| モジュール | 例 |
|---|---|
| Gateway 実装（Adapter） | `GeminiAiAdapter.ts`、`GitHubRestApiAdapter.ts` |
| Repository 実装 | `ReviewHistoryRepository.ts`、`BudgetLedgerRepository.ts` |
| UseCase（外部依存含む） | エンドツーエンドシナリオテスト |

### 前提

```bash
# 環境変数設定（.env.test）
INTEGRATION_TEST=true
DATABASE_URL=postgres://test:test@localhost:5432/test_db
UPSTASH_REDIS_REST_URL=...
UPSTASH_REDIS_REST_TOKEN=...
```

実行時に `INTEGRATION_TEST=true` が未設定の場合、Integration Test は自動スキップ。

### 配置ルール

```
test/integration/
├── infrastructure/
│   ├── adapters/
│   │   ├── gemini-ai.adapter.test.ts
│   │   ├── github-api.adapter.test.ts
│   │   └── ...
│   └── repositories/
│       ├── review-history.repository.test.ts
│       └── ...
└── application/
    └── usecases/
        ├── execute-pr-review.usecase.integration.test.ts
        └── ...
```

### ポイント

#### 1. DB 状態を必ず検証

**戻り値だけでなく、DB に永続化されたことを確認する。** これは Infrastructure テストの最重要ポイント。

```typescript
// 良い例: DB 状態を検証
describe('ReviewHistoryRepository', () => {
  it('should persist review history to Redis', async () => {
    const repo = new ReviewHistoryRepository(redisClient)
    
    const history = {
      prId: 'pr-123',
      reviews: [{ perspective: 'logic', score: 8 }],
      timestamp: new Date()
    }
    
    const result = await repo.save(history)
    expect(result.isSuccess).toBe(true)
    
    // DB から取得して確認
    const stored = await repo.findByPrId('pr-123')
    expect(stored.value).toEqual(history)
  })
})
```

#### 2. エラーケース・復旧シナリオをテスト

API エラー、接続失敗、リトライロジックを検証。

```typescript
// 良い例: リトライロジック検証
describe('GitHubRestApiAdapter', () => {
  it('should retry on rate limit (429)', async () => {
    const adapter = new GitHubRestApiAdapter(mockHttpClient)
    mockHttpClient.setResponse({ status: 429 })
    
    // リトライで成功するよう 2 回目以降を成功に
    mockHttpClient.onSecondCall().setResponse({ status: 200, data: {...} })
    
    const result = await adapter.getPrDiff(prId)
    expect(result.isSuccess).toBe(true)
    expect(mockHttpClient.callCount).toBe(2) // リトライ確認
  })
})
```

#### 3. トランザクション・ロールバック検証

失敗時に DB が清潔な状態に戻ることを確認。

```typescript
// 良い例: エラー時のロールバック確認
describe('ReviewHistoryRepository - Error Handling', () => {
  it('should not corrupt DB on error', async () => {
    const repo = new ReviewHistoryRepository(redisClient)
    
    // 不正データで保存試行
    const invalidHistory = { ...validHistory, prId: null }
    const result = await repo.save(invalidHistory)
    
    expect(result.isError).toBe(true)
    
    // DB から同じ prId を検索→記録なし
    const stored = await repo.findByPrId('pr-123')
    expect(stored.value).toBeUndefined()
  })
})
```

#### 4. 並列実行・重複データ対策

テストデータ ID に UUI またはタイムスタンプを含める。

```typescript
// 良い例: ユニークな ID 生成
const testPrId = `test-pr-${Date.now()}-${Math.random().toString(36)}`
const history = { prId: testPrId, ... }
```

#### 5. afterEach で必ずクリーンアップ

テストで作成したデータは削除。

```typescript
afterEach(async () => {
  await redisClient.del(`review:${testPrId}`)
  await db.delete('review_history').where({ prId: testPrId })
})
```

## テスト作成時の注意事項

### describe/it の構造化

関連するテストを `describe` でグループ化。テスト対象の**目的を明確に**。

```typescript
// OK - テスト意図が明確
describe('ReviewEngineService', () => {
  describe('#execute with TypeScript code', () => {
    it('should detect type safety issues', () => { ... })
    it('should suggest strict mode configuration', () => { ... })
  })

  describe('#execute with Python code', () => {
    it('should check PEP 8 compliance', () => { ... })
  })
})
```

### Deterministic Test（決定論的テスト）

**特に AI 生成の場合、結果が非決定的になりやすい。テストでは Mock/Stub を使って決定論的にする。**

```typescript
// 良い例: Mock で決定論的に
describe('SelfRefinementService', () => {
  it('should remove invalid suggestions on verification fail', async () => {
    const mockAi = new MockAiGateway()
    mockAi.generatePhase.setResponse('suggestion code here')
    mockAi.verifyPhase.setResponse({ valid: false, reason: 'syntax error' })
    
    const service = new SelfRefinementService(mockAi)
    const result = await service.refine(...)
    
    expect(result.suggestions).toEqual([]) // 無効な提案は削除
  })
})
```

## Mock/Stub 戦略

| 層 | 対象 | Mock/Stub | 理由 |
|---|---|---|---|
| **Unit Test** | Gateway（AI API、GitHub API） | Mock | 外部依存なし。決定論的テスト |
| **Unit Test** | Repository interface | Mock | DB 接続なし |
| **Integration Test** | Gateway（実装） | Real or Stub | DB 実装を検証 |
| **Integration Test** | Repository（実装） | Real | DB 操作を検証 |
| **Integration Test** | 外部 API（Gemini/GitHub） | Stub | API コスト・安定性の考慮 |
