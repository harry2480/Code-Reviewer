# Phase 4: 自己修正・背景抽出 実装計画

## 目的

**開発者が AI レビューの不正確さ（ハルシネーション・存在しない API 提案・PR 背景を踏まえない指摘）に振り回されず、信頼できる精密なレビューを受けられる状態にするため。**

具体的には、Phase 2 / 3 で実装した「4 つの眼」レビューエンジン + ポリグロット・エキスパート機構の上に、以下 2 つの精度向上機構を追加する：

| 機構 | 解決する問題 |
|---|---|
| **二段階検証（4.1 SelfRefinement Service）** | 生成フェーズ単独では「実在しない API 提案」「文法的に不正な suggestion code」「根拠なき断定」が混入する。検証フェーズを挟むことで、これらを自動削除し偽陽性を削減する。 |
| **背景抽出（4.2 ContextExtractor 強化）** | diff 単体ではコードの意図・影響範囲が掴めず、「すでに別所で対応済みの値検証を再要求する」「呼び出し元への破壊的変更を見落とす」など文脈不足の指摘が発生する。直近コミットメッセージと呼び出し元情報を推論に反映することで、文脈を踏まえた指摘へ昇格させる。 |

## 前提条件

- **Phase 2 完了済み**: `apps/webapp/src/backend/domain/services/review-engine.service.ts` が存在し、`buildSystemPrompt(perspective, languageRules?)` を提供する。
- **Phase 3 完了済み**: `apps/webapp/src/backend/domain/services/polyglot-expert.service.ts` および `apps/webapp/src/backend/application/usecases/execute-pr-review.usecase.ts` が存在する。`ExecutePrReviewUseCase.execute()` 内で diff 取得 → 言語検出 → perspective ごとに AI 生成 → ReviewComment 永続化のフローが組まれている。
- **Phase 1 で整備済み**: `AiGateway` / `GitHubApiGateway` / `ContextExtractorGateway`（interface のみ）/ `ReviewComment` モデルが存在する。

> 本ドキュメントは Phase 2 / 3 マージ後（`develop` に存在する状態）を前提に Phase 4 ブランチを切ることを想定する。

## 必要な環境変数

Phase 4 では新規環境変数は発生しない。Phase 1 / 2 で整備済みのものを再利用する。

| 環境変数 | 用途 | Phase 4 での利用箇所 |
|---|---|---|
| `ANTHROPIC_API_KEY` | AI 生成（既存 `AnthropicAiGateway`） | 検証フェーズの AI 呼び出し（生成と同じ Gateway を流用） |
| `GITHUB_TOKEN` | GitHub REST API（既存 `GitHubApiAdapter`） | 呼び出し元検索（Code Search API）・コミット取得（既存メソッド） |

未設定時の挙動：いずれも未設定の場合、composition で Stub アダプタが選択され、Stub の固定レスポンスで動作する（既存の挙動と同じ）。

## 設計方針

### 全体アーキテクチャ

Phase 4 は **ドメインサービス 1 つ追加 + Gateway interface 拡張 + UseCase オーケストレーション差し替え** の 3 段で構成する。アーキテクチャ依存方向（`presentation → application → domain ← infrastructure`）は崩さない。

```
ExecutePrReviewUseCase                 ← 既存（Phase 3）から拡張
  ├─ ContextExtractorGateway.extract*  ← interface 拡張（呼び出し元検索追加）
  ├─ ReviewEngineService.buildSystem*  ← 既存（Phase 3）
  ├─ AiGateway.generate                ← 既存（生成フェーズで利用）
  ├─ SelfRefinementService.verify      ← 新規
  │    └─ AiGateway.generate            ← 既存（検証フェーズで利用、別プロンプト）
  └─ ReviewCommentRepository.save      ← 既存
```

### 4.1 SelfRefinement Service の設計

#### 責務

- 生成フェーズで AI が出した raw レビューコメント文字列を入力に取り、**検証プロンプト**で別呼び出しを行い、各指摘について以下を判定する：
  1. **ハルシネーション検出**: 指摘が diff 中に実在する記述に基づいているか（実在しない関数名・API・行番号への指摘を除外）
  2. **提案コード有効性**: `suggestedCode` が指摘対象の言語として構文的に妥当か、かつ diff の対象行にそのまま貼り付けて意味が通るか
  3. **根拠妥当性**: 「危険」「非効率」などの断定が diff の内容で裏付けられるか
- 検証で失格した指摘は **削除**（regenerate せず単純除外）。Phase 4 ではコスト抑制のため「再生成」ではなく「削除のみ」とする。
- 検証結果（採用 / 削除の判定理由）は debug ログ・Analysis Chain 用に保持できるよう、`RefinementOutcome` 型で返す。

#### ドメインサービス配置

`apps/webapp/src/backend/domain/services/self-refinement.service.ts`

#### インターフェース概要

```typescript
export type RefinementOutcome = {
  acceptedComments: ReviewComment[];
  rejectedComments: { comment: ReviewComment; reason: string }[];
};

export class SelfRefinementService {
  constructor(private readonly ai: AiGateway) {}

  async refine(params: {
    diff: string;
    candidateComments: ReviewComment[];
  }): Promise<RefinementOutcome> {
    // 1. candidateComments を JSON で検証プロンプトに含める
    // 2. AiGateway.generate で「各コメントが妥当か」を JSON 配列で受領
    // 3. 結果に従い acceptedComments / rejectedComments に分配
  }

  // 内部ヘルパ。検証プロンプトの組み立て（純粋関数）。
  private buildVerificationPrompt(diff: string, comments: ReviewComment[]): {
    systemPrompt: string;
    userPrompt: string;
  } { ... }
}
```

- **入力**: `diff`（生 diff 文字列）+ 生成済み `ReviewComment[]`。
- **出力**: 採用 / 棄却に振り分けた `RefinementOutcome`。`Result<T, E>` を返さないのは、AI 呼び出し失敗は infrastructure 例外で吹き上げる方針のため（既存 ReviewEngineService の方針に合わせる）。
- **AI 呼び出し回数**: 1 回（候補コメント全件をまとめて 1 リクエスト）。perspective ごとには分けない（コスト最小化）。

#### 検証プロンプトの構造（プロンプト管理）

`apps/webapp/src/backend/domain/services/prompts/` 配下にプロンプト定数を置く（既存の Phase 2 / 3 のプロンプト管理場所を踏襲）。

- `SELF_REFINEMENT_SYSTEM_PROMPT`: 「あなたは厳格なレビュー監査官。実在性・構文・根拠を確認し、JSON 配列で各コメントを accept / reject 判定せよ」
- 出力フォーマット指定: `[{ "id": "...", "verdict": "accept" | "reject", "reason": "..." }]`

JSON パースに失敗した場合は **全件採用 fail-open** とし、ログに `parse-failure` を残す。検証フェーズの故障で生成結果が消えるのを防ぐ。

### 4.2 ContextExtractor Gateway 強化

#### 既存 interface の課題

```typescript
// 現状
export interface ContextExtractorGateway {
  extractContext(owner: string, repo: string, filePath: string): Promise<string>;
}
```

- `filePath` 単位の API になっており、複数ファイルへの呼び出しが非効率
- 戻り値が単一の文字列で、内訳（コミット履歴 / 呼び出し元）が判別できず、プロンプト組み立て側で構造化できない
- PR 番号を渡す引数がなく、コミットメッセージ取得（PR スコープ）と整合しない

#### 改修方針

interface を **PR 単位の文脈抽出** に再設計する。実装側で複数ファイルの呼び出し元検索を 1 リクエストに集約できるようにする。

```typescript
// 改修後
export type PullRequestContext = {
  recentCommitMessages: string[];          // 直近 N 件のコミットメッセージ
  callerReferences: CallerReference[];     // 変更されたシンボルの呼び出し元
};

export type CallerReference = {
  symbol: string;          // 検出した識別子（例: "authenticateUser"）
  filePath: string;        // 呼び出し元ファイルパス
  lineNumber: number;      // 呼び出し元の行番号
  snippet: string;         // 該当行前後の短いスニペット（最大 3 行）
};

export interface ContextExtractorGateway {
  extractPullRequestContext(params: {
    owner: string;
    repo: string;
    prNumber: number;
    diff: string;
  }): Promise<PullRequestContext>;
}
```

#### 呼び出し元検索のロジック（adapter 側）

`apps/webapp/src/backend/infrastructure/adapters/context-extractor.adapter.ts`

1. **diff から変更シンボルの抽出**:
   - diff のヘッダ `@@ ... @@` 直後の関数名 / クラス名 / メソッド名を正規表現で抽出
   - 抽出対象は最大 5 シンボル（コスト保護）
2. **GitHub Code Search API**:
   - 既存 `Octokit` クライアントを再利用し、`search.code({ q: 'symbol repo:owner/repo' })` を呼ぶ
   - 各シンボルあたり最大 3 件の `CallerReference` を取得
   - 自身の定義箇所（diff の対象ファイル）は除外
3. **コミットメッセージ取得**:
   - 既存の `GitHubApiGateway.getCommitMessages` を **そのまま再利用しない**（adapter 同士の依存を作らないため）
   - Octokit を直接呼び出して `pulls.listCommits` を実行し、最新 5 件まで取得

> ※ この adapter は `GitHubApiAdapter` と Octokit インスタンスを共有しないが、composition でトークンを共有してそれぞれ初期化する。adapter 同士の直接参照は禁止。

#### Stub Adapter の追加

`apps/webapp/src/backend/infrastructure/adapters/stub-context-extractor.adapter.ts`

- `recentCommitMessages` は固定値（例: `['feat: stub commit']`）
- `callerReferences` は空配列または 1 件の固定 stub
- composition で `GITHUB_TOKEN` 未設定時に選択

#### UseCase での組み込み

`ExecutePrReviewUseCase.execute()` の流れを以下に拡張する：

```
[Phase 3 までのフロー]
1. diff 取得 (githubGateway.getPullRequestDiff)
2. commitMessages 取得 (githubGateway.getCommitMessages)
3. PolyglotExpertService.detectLanguages → buildLanguageRulesPrompt
4. for perspective in PERSPECTIVES:
     4-1. systemPrompt = reviewEngine.buildSystemPrompt(perspective, languageRules)
     4-2. raw = ai.generate({systemPrompt, userPrompt: diff + commitMessages, ...})
     4-3. parse → ReviewComment[]
5. 全 ReviewComment を repository に保存

[Phase 4 拡張後のフロー]
1. diff 取得
2. context = contextExtractor.extractPullRequestContext({owner, repo, prNumber, diff})
   ※ commitMessages 単独取得は廃止し、context.recentCommitMessages を利用
3. PolyglotExpertService.detectLanguages → buildLanguageRulesPrompt
4. for perspective in PERSPECTIVES:
     4-1. systemPrompt = reviewEngine.buildSystemPrompt(perspective, languageRules)
     4-2. userPrompt = buildUserPrompt(diff, context)  ← 新規ヘルパ
     4-3. raw = ai.generate({systemPrompt, userPrompt, ...})
     4-4. parse → candidate ReviewComment[]
5. outcome = selfRefinement.refine({diff, candidateComments: 全 perspective の合計})
6. outcome.acceptedComments を repository に保存
```

- `buildUserPrompt` ヘルパは UseCase 内（または `review-engine.service.ts` の static method）に置く。プロンプト本体には diff だけでなく、`## Recent commits` セクションと `## Call sites of changed symbols` セクションを追加する。
- `getCommitMessages` の Gateway メソッドは **Phase 4 では削除しない**（他から呼ばれていない場合は Phase 7 のクリーンアップで削除）。

## テスト戦略

### Unit Test（4.1 SelfRefinement Service）

`test/unit/domain/services/self-refinement.service.test.ts`

| ケース | 検証内容 |
|---|---|
| 全件 accept | AI が全コメントを `accept` 判定した場合、`acceptedComments` に全件、`rejectedComments` は空 |
| 一部 reject（ハルシネーション） | AI が一部を `reject: hallucination` と返した場合、当該コメントが `rejectedComments` に分配され `reason` が保持される |
| 提案コード無効 | AI が `reject: invalid-suggestion` と返した場合の分配 |
| AI レスポンス JSON パース失敗 | fail-open で全件 accept し、`rejectedComments` は空（ログ出力は副作用なので検証対象外） |
| 候補 0 件 | AI を呼ばずに空 outcome を即返す（呼び出し回数 0 を検証） |
| AI 呼び出し例外 | 上位に throw されることを検証（catch しない方針） |

`AiGateway` は test double（簡易 mock クラスまたは `vi.fn()` で `generate` を差し替え）で注入する。

## アーキテクチャ整合性チェック

- [x] `domain → 他層` への依存なし（`SelfRefinementService` は `AiGateway` interface のみに依存）
- [x] `application → infrastructure` への直接依存なし（UseCase は Gateway interface のみ受け取る）
- [x] `infrastructure → domain/gateways` のみ依存（`ContextExtractorAdapter` は Gateway interface を implements）
- [x] composition 層が唯一の DI 組み立てポイント
- [x] Stub 実装を必須化（`StubContextExtractorAdapter`）
- [x] 命名規約準拠（`*.service.ts` / `*.gateway.ts` / `*.adapter.ts` / `*.composition.ts`）
- [x] Domain 層は `Result<T, E>` を返す方針を維持（`SelfRefinementService` は内部例外を上位に throw する設計を採用しない場合は `Result` 型へ変更検討）

> **要検討**: `SelfRefinementService.refine` の戻り値を `Result<RefinementOutcome, RefinementError>` にすべきか。Phase 2 / 3 の `ReviewEngineService` の方針に合わせる。実装着手時に Phase 2 / 3 の実コードを確認して整合させる。
